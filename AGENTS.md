# Agent Guidelines

## Project Overview

Pizza World is a fullstack app: Spring Boot 4 (Java 21, H2) backend + React 19 (Vite, TypeScript) frontend. The frontend is deployed to Vercel; the backend is not deployed. The frontend uses mock data fallback when the API is unavailable (see `frontend/src/api.ts`).

## Tech Stack

- **Backend:** Spring Boot 4, Java 21, Spring Data JPA, H2 in-memory database
- **Frontend:** React 19, TypeScript, Vite, plain CSS (no UI libraries)
- **Build:** Gradle (backend), npm (frontend)
- **Deploy:** Vercel (frontend only)

## Jira

Tasks for this repository live in Jira project **PZG**: https://jetbrains-team-bitdsbm5.atlassian.net/jira/software/projects/PZG/boards

- Work only on issues from project `PZG`. When given an issue key (e.g. `PZG-1`), read the issue first: summary, description, acceptance criteria.
- Move the issue to **In Progress** when you start.
- Include the issue key in the branch name and every commit message (this links them to the issue in Jira):
  - Branch: `feature/PZG-1-short-name` (use `fix/PZG-6-short-name` for bugs)
  - Commit: `PZG-1: Add pizza ratings endpoint`
- When done: add a comment to the issue with a short summary, the branch name and the Vercel preview URL, then move it to **In Review**.

## Runtime logs & incidents

The frontend calls a Vercel Function, `frontend/api/checkout.ts` (`POST /api/checkout`), that prices the cart. It writes **one JSON log line per request** to Vercel runtime logs:

```json
{"ts":"…","level":"error","service":"checkout","event":"checkout","requestId":"…","status":500,"durationMs":3,"fault":null,"errorType":"TypeError","error":"…","stack":"…","deploymentId":"dpl_…"}
```

- `level`: `info` (200), `warn` (400, bad input), `error` (500, a bug). A function timeout shows up as a 504 with no JSON line.
- Read logs: `cd frontend && vercel logs <deployment-url>`
- Fault injection for demos: the Vercel env var `CHECKOUT_FAULT` = `error` | `slow` | `bad-promo` (optional `CHECKOUT_FAULT_RATE` 0..1). Do not change it unless the task asks you to.
- Synthetic monitor: `BASE_URL=<deployment-url> npm run synthetic --prefix frontend` — exits non-zero if checkout is broken. It also runs every 15 minutes against production.

When fixing an incident: reproduce it from the log line (`error`, `stack`, `requestId`), add a regression test in `frontend/tests/`, deploy a preview, and run the synthetic monitor against the **preview URL**. Include the result in the Jira comment.

## How to Work on Tasks

### 1. Create a feature branch

```
git checkout -b feature/PZG-<number>-<short-name>
```

### 2. Backend changes (Spring Boot)

- Entities go in `src/main/java/com/jetbrains/pizzaworld/model/`
- Repositories in `src/main/java/com/jetbrains/pizzaworld/repository/`
- Controllers in `src/main/java/com/jetbrains/pizzaworld/controller/`
- DTOs in `src/main/java/com/jetbrains/pizzaworld/dto/`
- Seed data in `DataInitializer.java`
- Always add tests in `src/test/java/com/jetbrains/pizzaworld/`
- Run `./gradlew test` to verify

### 3. Frontend changes (React + TypeScript)

- Components in `frontend/src/components/`
- API calls in `frontend/src/api.ts`
- Types in `frontend/src/types.ts`
- Styles in `frontend/src/App.css`
- **Important:** When adding new API calls, always provide mock data fallback using `tryFetch()` so the feature works on Vercel without a live backend
- Server code (Vercel Functions) in `frontend/api/`, its tests in `frontend/tests/`
- Run `cd frontend && npm run lint && npm run build && npm test` to verify

### 4. CI

GitHub Actions (`.github/workflows/ci.yml`) runs on every push and PR: backend `./gradlew test`, frontend `npm ci`, `npm run lint`, `npm run build`, `npm test`. A PR is ready for review only when CI is green — if it fails, read the job log and fix it before asking for review.

### 5. Code Style

- Frontend: minimal, clean UI inspired by [Studio Pallesh](https://www.studiopallesh.nl/) — lots of whitespace, serif headings (DM Serif Display), sans-serif body (Inter), neutral palette
- Backend: standard Spring Boot conventions, no Lombok
- Keep changes focused — one feature per branch
- Write tests for new endpoints

### 6. Push and Deploy

Push the feature branch:

```
git push -u origin feature/PZG-<number>-<short-name>
```

Deploy a preview using the Vercel CLI and grab the URL. The `frontend/` directory is already linked to the Vercel project via the committed `frontend/.vercel/project.json` — do not run `vercel link` and do not change the project:
```bash
cd frontend
vercel --yes 2>&1 | grep -oE 'https://[^ ]+\.vercel\.app' | tail -1
```

This prints the preview URL (e.g. `https://pizza-world-github-<hash>-junie.vercel.app`). The hash is generated by Vercel — always use the real URL from the CLI output.

### 7. Summary

**Always** end your task summary with a clickable Vercel preview link. Use this exact format:

```
## Done

PZG-1 — Added pizza ratings feature:
- Backend: `rating` field on Pizza entity, `GET /api/pizzas/top` endpoint, tests
- Frontend: star rating display in gallery items with mock fallback

**Jira:** https://jetbrains-team-bitdsbm5.atlassian.net/browse/PZG-1
**Branch:** `feature/PZG-1-pizza-ratings`
**Preview:** https://pizza-world-github-abc123-junie.vercel.app
```

The preview URL **must** come from the `vercel` CLI output (see above). Do not guess or construct the URL manually — always use the real URL. It must be a full clickable link, not inside a code block.
